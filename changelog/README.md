# changelog —— 改动台账

**这个目录回答四个问题，而这四个问题 `git log` 都答不好：**

| 问题 | 为什么重要 |
|---|---|
| **为什么改？** | 「修了 `_round_end_ack`」看不出所以然；「老版那个闸是每弹窗新建的闭包，新版做成成员却在 `reset_balance` 里清」才看得出 |
| **怎么验证改对了？** | 每条的判据是**哪个门禁的哪一项**、期望输出长什么样 |
| **改了要付什么代价？** | 有没有碰 `ast_parity` 的冻结基线、`trace_parity` 的 sha1 变没变 |
| **怎么回退？** | 回退动作是**语义描述**（"把清标志挪回 `reset_balance`"），不是行号 |

---

## ⚠️ 先说清楚：这不是版本控制，也不能替代版本控制

**回退需要的是精确 diff，而这里写的是人话。** 想回退，正解是版本控制。

而 `new_danzhu/` **现在还不是 git 仓库**（`ls -d .git` = 无）。这是当前最大的工程风险 ——
到目前为止的**全部改动都没有任何可回退的机制**。

### 和 git 的分工

```
git            → 精确的「改了什么」+ 一键回退（git revert / git diff / git bisect）
changelog/     → 「为什么改」「怎么验证」「什么代价」—— commit message 装不下的那部分
```

**两者都要。** 而且对 `new_danzhu/` 来说，`git init` 还顺手解决第二件事：

> 报告 §11.3 记着：`.github/workflows/build-apk.yml` 的触发/缓存/产物路径**都假定仓库根就是
> `new_danzhu`**（老版是拿 `android/` 当独立仓库根）。所以**要发 APK 本来就得让它自己 `git init`**。

```bash
cd new_danzhu
git init
git add -A
git commit -m "基线：重构落地 + 30 条门禁全绿（trace sha1 2b830486…）"
```

⇒ 这一条命令同时买到「能回退」和「能发 APK」。**在跑它之前，任何改动都只能靠改回去。**

## 没有 git 时的临时探针：`baseline.sha256`

```bash
python changelog/_mksum.py            # 重拍指纹（31 个出货文件）
python changelog/_mksum.py --check    # 与基线比对：列出 [改了] / [新增] / [没了]
```

它只覆盖**出货文件**（`danzhu/**/*.py` + `main.py`），不含 `tests/` 与 `temp/`。

⚠️ 它只能回答「**变没变**」，回答不了「变成什么」，更**不能回退**。
   它存在的唯一理由是：在还没有 git 之前，至少能一眼看出动过哪些文件。
   **`git init` 之后就不需要它了** —— 别把它当成版本控制用。

## 一条记录长什么样

每条一个 `###` 小节，编号在日期文件内单调递增。**六个字段，缺一不可**：

```markdown
### N. 一句话标题（说清"什么坏了"，不是"改了哪里"）

- **日期**：2026-09-19
- **类型**：真分歧修复 / 新版引入的回归 / 性能 / 内存 / 门禁新增 / 对账覆盖 / 清理
- **对账影响**：`trace_parity` sha1 **变 / 不变**；`parity` 273,090 项 **变 / 不变**
- **门禁代价**：无 / **动了 `ast_parity` 冻结基线**（若是，写清为什么非动不可）
- **验证**：跑哪条、期望输出是什么

**症状**：玩家/系统会看到什么（不是"代码不规范"）

**根因**：老版怎么做、新版怎么不一样

**改了哪里**：文件 + 函数名（**行号会漂，所以写函数名**）

**怎么回退**：把什么改回哪里 —— 语义描述；精确 diff 靠 git
```

### 两条写记录的纪律

1. **「新版引入的」必须如实标**。本工程 10 处真分歧**全部**是重构自己引入的
   （老版没有），拿它们当"重构的成果"是循环论证 —— 它们是**风险账单**。
   标错了，下一个人会以为老版有这些 bug。
2. **行号只作参考**。写 `game.py:1398` 这种锚点行号，半年后一定漂。
   **以函数名 + 语义为准**。
