## 1. `_load_config` 的 `try` 作用域被收窄 ⇒ 坏存档启动即崩

- **日期**：2026-09-19 ｜ **类型**：真分歧修复 ｜ **对账影响**：sha1 不变 ｜ **门禁代价**：无
- **验证**：`python tests/parity.py`；构造 `{"balance": 1e400}` 的存档，两版对照行为

**症状**：存档里出现 `1e400` / `Infinity` 时，新版 `App.build()` 里抛 `OverflowError` 直接冒到 Kivy 主循环 ⇒ **启动即崩、进不去游戏**。老版同一份存档照常启动。

**根因**：老版 `try` 罩住**整个解析块**（`main.py:20566` 起 22 行）；重构时被收窄成只罩 `open()+json.load`，22 行解析裸奔。
触发面是真实的：`json.loads('1e400') == inf`，而 `json.dump(float('inf'))` 写出来的正是裸 `Infinity` —— **能被 `json.load` 读出 `inf` 的存档是合法 JSON**，不走"解析失败"那条 `except`。

**改了哪里**：`danzhu/game.py` 的 `_load_config` —— 把 `try` 恢复成罩住整个解析块。

**怎么回退**：把 `try` 缩回只罩 `open()/json.load` 两行。（回退后 `auto_reset` / `persist_check` 仍会绿，**只有构造坏存档才抓得到** —— 这就是它当初溜过去的原因。）

## 24. 包名 `org.danzhu.plinko` → `org.danzhu.tiao` —— 让新版能与老版 APK **共存**

- **日期**：2026-09-19 ｜ **类型**：打包配置（用户要求） ｜ **对账影响**：无 ｜ **门禁代价**：无
- **验证**：`pack_scope` / `lint_gate` 绿；⚠️ **包名是否真生效要装到真机上看**（见末尾）

**症状（用户问的）**：「你这个软件和之前的那个游戏能不能同时安装共存？」—— **不能**。查证：

| | 新版 | 老版 |
|---|---|---|
| 包名 | `org.danzhu.plinko` | `org.danzhu.plinko` |
| versionCode | `1000000` | `1000000` |
| 签名 | debug 证书 A | debug 证书 B（**不同**） |

三者叠在一起 ⇒ 安卓认为它们是**同一个应用**；而签名不同 ⇒ 装新版报
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`，**只能先卸载老版** ⇒ **存档全清**（余额/轮次/跑分历史）。
这正是 `buildozer.spec:30-33` 那段注释警告过的场景。

⚠️ 两个证书的 subject 都是 `Android Debug`，但**字节不同** —— debug keystore 是**每台机器
首次构建时随机生成**的，跨机器天生不兼容。本机实测（两个 APK 的 `META-INF/CERT.RSA`）：
新版 sha256 `cd57d8b9a891235fa7485409c17a191e…` / 老版 `6546e281d2781ad23533ce84809cebcb…`，
都是 1167 字节。

**改了哪里**：
1. `buildozer.spec`：`package.name = plinko` → **`tiao`**（`package.domain` 不动）
   ⇒ 应用 ID 变成 `org.danzhu.tiao`
2. `.github/workflows/build-apk.yml`：artifact 名 `plinko-apk` → **`tiao-apk`**（否则会误以为下错包）

**为什么这样就够**（逐条查证过）：
- **存档全部走 `user_data_dir`**（`/data/data/<包名>/files`）⇒ 换包名 = **天然隔离**，
  老版那份原样保留。这就是共存要的效果。
- 诊断日志那条降级链：第②级 `getExternalFilesDir`（`/sdcard/Android/data/<包名>/`）与
  第③级 `user_data_dir` 也含包名；只有第①级公共 Download 是共享的，而文件名带时间戳不会撞。
- ⚠️ `java/com/plinko/SoundGate.java` **不受影响** —— 它的 `package com.plinko;` 是**独立的
  Java 包名**，与这个应用 ID 无关；全文也没引用 p4a 生成的 `PythonActivity`
  （只 import `android.media.SoundPool` / `android.os.SystemClock` / `java.util.*`）。
- **Python 侧对旧包名的引用：零**。全仓 grep `org.danzhu` 只有 `buildozer.spec` 一处；
  `danzhu/audio/backend.py` 里的 `com.plinko.SoundGate` 是 **Java 类名**，不走应用 ID。

**用户决定**：桌面显示名**不改**（两个都叫「跳跳的弹珠机」）。
⚠️ 后果：同一台手机上两个图标**同名**，只能靠位置/包名区分 —— 用户知情并确认。

**怎么回退**：`package.name` 改回 `plinko`，artifact 名改回 `plinko-apk`，重新构建。

⚠️ **本条只验到"配置改了"**：包名是否真生效、两个包能否同时装上，
**要等云构建出 APK 后装到真机上看**（系统设置 → 应用信息，看包名是否为 `org.danzhu.tiao`）。

## 27. 「游戏信息」面板：**可跑核并进 CPU 那一行**（省下一行）

- **日期**：2026-09-19 ｜ **类型**：界面调整（玩家定） ｜ **对账影响**：无 ｜ **门禁代价**：**动了 `ast_parity` 冻结基线**（`_live_cpu_freq_line` 一条，理由见下）
- **验证**：`ast_parity` freeze 后全绿（161 条逐条相同）；`fx_gates` FAIL **18 vs 18 逐条相同**；
  `trace_parity` **sha1 一位未变**（`2b8304864bfbc664df273795f489d76f434e0fcf`）；
  探针实测行数 **5 → 4**

**玩家原话**：「把可跑核 x-y，放在 CPU:X核 x+Y 后面 多个空格即可」+「这样可以节省1行」

**改前 / 改后**（`_live_cpu_freq_line()` 的输出）：

```
改前(5 行)                        改后(4 行)
CPU：8 核　1+3+4                  CPU：8 核　1+3+4　　可跑核 4-7
　核 7　3187M　当前 1804M          　核 7　3187M　当前 1804M
　核 4-6　2745M　当前 2400M        　核 4-6　2745M　当前 2400M
　核 0-3　2016M　当前 2800M        　核 0-3　2016M　当前 2800M
　可跑核　4-7
```

**为什么这么改是对的**：可跑核和「几个核」本来就是同一件事的两面（都是"这台机器有多少核能用"），
单独占一行白吃一块高度 —— 而那块面板**行数是有硬预算的**。

**两处实现细节**：
1. 分隔用**全角空格**（`　　`），不是 ASCII 空格 —— 夹在汉字/全角括号之间时 ASCII 空格太窄，
   会挤成「1+3+4可跑核」。本行其它分隔（`核　%s`）本来也都是全角。
2. 亲和性的读取从**函数尾部挪到头部**（要在拼第一行之前拿到）—— 逻辑一个字没改，
   `os.sched_getaffinity(0)` 仍然包在 try 里、拿不到就整段不印。

⚠️ **折行不会裁切**（这条专门查过）：窄屏（等效 360 / 系统字体 1.3 倍）上这行可能折成两句 ——
`_mk_lbl` 自动撑高，且开窗后 `_popup_fit_content` 按**真实排版**重算弹窗高度 ⇒ 弹窗跟着长高，
不会把尾巴裁掉。所以**不需要**改 `_n_extra`（那块 Label 无论几行都只算 1 个控件）。

**顺带修了判据的一处回显错误**：`fx_gates.py` 那条「可跑核」的 check 原来只断言
`"可跑核" in _got`（任意行），**回显**却取 `_got.split("\n")[-1]` —— 现在可跑核在第一行了，
那个回显会指向最后一行（核 0-3）。已经改成断言 **`"可跑核" in _got.split("\n")[0]`** 并把回显改 `[0]`：
判据从"在哪都行"收紧成"必须在第一行"，正是玩家这次的要求。

**怎么回退**：把 `_aff` 那段拼回第一行的写法删掉、恢复函数尾部那个 `_lines.append("　可跑核…")`，
再 `python tests/ast_parity.py --freeze`。

## 28. 切档不再**整块重画**盘面 —— `set_rtp` 改走增量 `_update_slots()`

- **日期**：2026-09-19 ｜ **类型**：性能（老版交接文档**方案四**） ｜ **对账影响**：无 ｜ **门禁代价**：**动了 `ast_parity` 冻结基线**（`set_rtp` 一条）
- **验证**：`trace_parity` **sha1 一位未变**；`ast_parity` freeze 后全绿；`fx_gates` FAIL **18 vs 18 逐条相同**

**出处**：老版专门留的交接文档 `android/jiaojie.md`（2026-09-14，《1% Low 后续优化交接》）
**方案四**原文：

> 现有代码已将"仅倍率槽变化"改为 `_update_slots()`。下一步**只检查仍然触发整块
> `GameArea._redraw()` 的真实场景**：尺寸变化、首帧、重置、**切换档位**、异常兜底。

**查证**（全工程只有一处）：`"redraw"` 事件**只从 `Game.set_rtp` 发出** —— 其余 `_redraw()`
调用都是「尺寸/位置变了」（`self.bind(size=_redraw, pos=_redraw)`）或结构守卫兜底。所以这一处
就是方案四点名的那一类。

**症状**：切档时几何**一点没变**（变的只有 `multipliers` 那 9 个值），却走
`canvas.clear()` + 重建全部画布指令 —— 桌面实测 **0.529ms**、真机约 **9ms**，
而 165Hz 的帧预算只有 **6.06ms** ⇒ 那 9ms 正好是一记肉眼可见的卡顿。

**改成什么**：`self._emit("redraw")` → **`self._emit("update_slots")`**，与 `park_ball` 重掷
（同一种改动：只变 9 个槽）走同一条路。

**逐条核过为什么等价**：
- `_update_slots()` **自带结构守卫**（9 个槽的列表长度对不上就自己退回 `_redraw`）⇒ 首帧 /
  尺寸刚变过 / 槽数变了这些情形**不会被半更新**。
- 它顺手做的事与 `_redraw` **等价**：作废槽位白闪（`_pulse = None`）+ 熄灭全部投中指示灯
  （`lamps_off()`）—— 后者本来就是 `_redraw` 重建 `_lamp_cols` 时**顺手**做的。
- 特效（中奖大字/杯子）不受影响：`_redraw` 只在**尺寸真变了**才清特效，而 `_update_slots`
  根本不清画布 ⇒ 两条路都不动它们。
- ⚠️ **红线验证**：`trace_parity` 的脚本**确实会切档**（`tests/trace.py:916` 换必中档、
  `:966` 换返还率档），而它采的是 28 个控件的几何 + 5355 帧 × 8 字段 —— **sha1 一位未变**
  ⇒ 两条路的**几何终态完全相同**，这不是推断，是实测。

**⚠️ 顺带被门禁逮住的一个夹具缺口**：改完 `fx_gates` 当场崩在
`AttributeError: '_GA' object has no attribute '_update_slots'` —— 那个假 `game_area` 桩件
只实现了 `_redraw`（因为老版 `set_rtp` 只会调它）。已给桩件补上 `_update_slots`。
**教训**：桩件必须跟着**出货代码真实会调的方法**走，少一个就是假红/假绿。

**怎么回退**：`self._emit("update_slots")` 改回 `self._emit("redraw")`，
再 `python tests/ast_parity.py --freeze`。
