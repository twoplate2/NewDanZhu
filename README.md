## 怎么知道"重构版和老版一样"

这是本工程和"另写一个弹珠机"的根本区别。**不靠肉眼比对，靠逐位对账。**

老版 `main.py` 可以**无窗口 import**，而且**同一随机种子 → 逐帧确定**。所以验收口径是
「同种子逐位相等」，不是「跑起来看着差不多」。

```

python tests/trace_parity.py    # ★ UI 行为对账（整局游戏）· 见下
python tests/audio_gates.py     # 音频层门禁 11 条 / 80 项断言，每条带阴性对照
python tests/bench_smoke.py     # 跑分链冒烟（18 个入口，只求"不炸"）
python tests/landscape_check.py # 横屏反旋转（轨迹台把窗口钉竖屏，这条分支从没被跑过）
python tests/canvas_order.py    # 画布层序（「顺序即层序」这条红线，原一条断言都没有）
```

⚠️ `--which new --verify` 打**两种**口径，证明力完全不同：**跨版本**（vs `trace_old.json`，
只忽略 `meta.driver`）才是"与老版逐位一致"的唯一证据；**可复现**（vs 自己上一次）只证明
确定性。曾经只有后者 —— 那是个**假绿**口径：重录一遍就能"制造绿"，实测漏掉过
5159 帧里 1320 帧不同、少 15 声落球音的一整次运行。现在两条都跑，跨版本红即返回非零。

### `trace_parity.py` —— 最强的那个闸门

同一个脚本录制台（12 发球 + 两次切档 + 一次"必中档中奖后不点击" + **长蓄力/飞行中重置/长按标题**）分别驱动老版与新版，
逐段比：

| 段 | 项数 | 内容 |
|---|---|---|
| 帧 | 5355 × 8 字段 | state / power / ball(x,y,vx,vy) / balance / round_plays / plays / hits / fx |
| 状态迁移 | 51 | 每次迁移的帧号、时刻、from/to、原因 |
| 结算 | 8 | 槽位、投注、档位、结算前后余额、彩蛋标记 |
| 音效 | 256 | **真发出去的**那一声（过了五道闸）：名字/增益/节流/帧/时刻 |
| 布局 | 28 控件 × 2 段 | 每个控件的 (x, y, w, h) |

**当前：全绿，且除 `meta.driver` 外逐字节相同**（sha1 `2b8304864bfbc664df273795f489d76f434e0fcf`）。

⚠️⚠️ **它驱动的是固定剧本, 有明确的覆盖洞**（2026-09-19 记）—— 剧本是
「12 发球 + 两次切档 + 一次必中档中奖后不点击」，**2026-09-19 扩过一轮**（下面标 ✅ 的都是新补的）：

| 没覆盖的输入 | 后果（已实测过的例子） |
|---|---|
| **蓄力 > 3 秒**（兜底自动发射） | ✅ **2026-09-19 已补进剧本**（第 4/8/12 发按住 200 帧）：帧数 5159→**5462**、音效 266→**275**，两版逐字节相同。⚠️ 但**它抓不到那个缺陷本身** —— 实测把 `_render_skip` 修复回退掉，sha1 **一模一样**（多出的那次 `_set_label_text` 是**幂等的**） |
| **飞行中按重置** | ✅ **2026-09-19 已补**（第 6 发飞 25 帧后 `reset_balance()`）：补的是 `reset_balance` 里那句「强制中断 charging/flying/misfire/landing 回 ready」—— 此前**从没被驱动过**。两版逐字节相同 |
| **长按标题 3 秒**（⇒ 跑分菜单） | ✅ **2026-09-19 已补**（剧本末尾成对置 `_bench_start` + `_bench_triggered` 后推 200 帧，与 `_on_title_touch_down` 同形）：补的是 `_check_title_hold` 发 `bench_menu` ⇒ `_show_bench_menu` 那一段。两版逐字节相同。⚠️ 只置 `_bench_start` 会 `AttributeError` —— **老版 `_bench_triggered` 从不在 `__init__` 里建**（`main.py:14236-14237` 成对置）|
| **跑分菜单内部导航** | ✅ **2026-09-19 已补**（长按标题后驱动「游戏信息」，菜单项两版同名 `main.py:15264` / `bench.py:985`）。两版逐字节相同 |
| 跑分菜单里**点「开始测试」跑一轮** | 未补 —— 那要**逐版本在弹窗里找控件**（两版控件树不同）。⚠️ 但那条路的价值（`_act` 同拍派发）**已由 `act_gate.py` 从调用形状上守住了**，轨迹再覆盖一遍是冗余 |

⇒ **"`trace_parity` 全绿"只等于"剧本覆盖到的那部分一致"**, 不等于"全部一致"。
⚠️⚠️ **更要紧的一条：轨迹对账看不见"多做一次幂等调用"这一类缺陷** ——
它比的是**可观测状态**（帧字段/迁移/结算/音效/布局），幂等调用不改变任何一项。
⇒ 这一类只能靠**调用侧**的判据抓：`render_skip.py`（行为）、`act_gate.py`（调用形状）。
**扩剧本对这个类别无效**（实测过）。

### `fx_gates.py` —— 演出/UI 层的 380 条，判据是「集合相同」

老版 `tools/fx_probe.py`（3240 行）是演出/UI 层的桌面自检 —— `bench.py`（5100+ 行）
目前**唯一**的验收规格。端口时 `check()` 调用点 **396 = 396**，逐条一致。
（⚠️ 那个 **396 是端口当时**的数字，是历史事实，**别改它**。新版此后陆续有新增 ——
2026-09-19 实测 **407** 条，其中 9 条钉的是「游戏信息」面板那条 CPU 频率实时行，
见 `changelog/2026-09-19.md` 第 23 条。**新增 check 不参与 FAIL 集合对账**（老版没这东西），
但每一条都做了阴性对照。）

**它自己就有 18 条 FAIL**（mipmap 没开、「中位跑分」文案已改…），那是老版**已知且接受**的
状态。所以判据是：

> **FAIL 集合必须与老版逐条相同。** 多一条 = 新版真错了；少一条 = **门禁被削弱了**。
> 两者都判红；老版基线读不到也判红（"没比"不等于"通过"），基线是
> `tests/golden/fx_probe_old.txt`（采自老工程，只读冻结）。

三条阴性对照都验过（多一条红 / 少一条红 / 基线缺失红）。

⚠️ **其中 2 条 check 的判据在 2026-09-19 改成了「运行期」**（当时 `check()` 调用点仍是 396 = 396，
只是它们的**判据内容**不再逐字照抄老版）—— 原先它们比对的是**源码字符串在不在**，那个形状
有两个洞：① **注释里出现同样字样就能喂绿它**（真踩过：一条解释这个弱点的注释把另一条检查
喂绿了）；② 老版那 8 处 `_brk_wrap` 是模块级调用，新版集中进 `_brk_install()` 后**只要函数
定义了却没被调用**，字符串照样在、检查照样绿，而跑分面板那 8 格子步骤计时**永远是 0**。
现在改成 import 之后看方法是不是真被包上（`_brk_wrap` 的包装器 qualname 是
`_brk_wrap.<locals>.f`），**阴性对照验过**：注释掉 `_brk_install()` → 新版 20 条 FAIL、判红。

### 与老版最大的结构差别

老版把「游戏逻辑」和「Kivy 界面」焊在一个 8263 行的 `RootWidget` 里。新版劈成两半：

```
danzhu/game.py :: Game            无头状态机 —— 六态 / 账务 / 音效决策 / 时序
ui/root.py     :: RootWidget      界面壳   —— 建控件树 / 把事件画出来 / 把输入转回去
```

`Game` **不播声、不画界面**，只产出 `Ev`。UI 每帧 `game.step(dt)` 然后逐条派发。
于是「同一串输入 → 同一串可观测轨迹」变成**可测**的 —— `trace_parity.py` 就是靠它。

`RootWidget` 那 8263 行按职责再拆成三个 Mixin（`ui_base` / `play` / `bench`），
老版的方法体一个字没动，只换了归属文件。

## ⚠️ 两条硬警告

**1. 字体是裁剪子集，不是完整中文字体。**
`fonts/NotoSansSC-Medium.otf` 只有 **1602 个码位 / 1444 个汉字**。新写一句 UI 文案，
只要含字库外的字，**真机上就是一个方块**，而桌面（系统字体兜底）截图看不出来。
老版为此让过 4 次路：「摄氏度」写成「度」、「每瓦跑分」写成「每W跑分」、
删掉带「群」的脚注、结论「UI 文案别用全角冷门符号」。
→ 加完文案跑 `python tests/font_check.py`，它只扫**真字符串字面量**（注释/docstring 不算）。

> 顺带一提，**老版自己还有两处漏网的豆腐块**，都是 `font_check.py` 扫出来的：
> ① 启动诊断里的「没登**记**到样本」（那个「登」不在自己的字体子集里）；
> ② 探针结论里的「**杠杆**在样本数上」（那个「杆」也不在）。
> 新版分别改成「没有样本」「关键在样本数上」（含义不变）。

**1b. 字体是「注册过」的，那条注册线不能掉。**
Kivy 默认字体不含汉字。老版 `main.py:486-493` 在**导入期**把子集字体注册成 `"Roboto"`；
新版端口时这一整条**没落地**，后果**全程静默**：真机中文全变方块，且 `text_px` 的宽度
全变（实测 `text_px("未中",48,True)` 96 → 42、"中奖! +100" 231 → 177）⇒ 自适应字号、
弹窗排版、槽位文字全线跟着错，而**没有任何报错**。
→ `font_check.py` 现在静态钉住这条注册（必须是**模块级**语句；塞进函数里等于没注册）。
端到端由 `trace_parity.py` 的布局段兜底 —— 那 28 个坐标就是 `text_px` 算出来的。

**2. 老版的注释和文档会骗人，代码才是唯一真值。**
实测已发现 4 处注释与代码不符（`MISFIRE_V_MAX` 注释 980 实际 935、`PEG_BOUNCE_VY_MAX`
注释 300 实际 280、`ARC_OUT_ANGLE` 注释残留 25° 实际 35°、`LAND_BOUNCE_MIN_VY` 文档 220 实际 440）。
根目录 `CLAUDE.md` 的参数表与安卓版对不上；`android/CLAUDE.md` 的「天花板<10%」
实测是 16.7%。**任何数值都必须从代码的赋值行读。**

## 已知的、刻意的差异

对账台上的每一处差异都必须能解释。目前这一条是**刻意保留**的：

**音频烘焙与运行期共用同一条随机流（`_ARNG`）。** 撞钉音色变体
（`pick_peg_variant`）抽的就是烘焙那条流，而烘焙跑在**后台线程**上 ——
完成时刻与游戏循环赛跑，谁先谁后**在任何一版里都不确定**（`bake_bank` 开头会 `seed`，
所以只有"跑没跑完"这一个变量）。

`trace.py` 的 `quiesce_audio()` 把这条竞态消掉：`join` 烘焙线程 + 把流钉回种子起点。
**这只钉起点、不钉消耗** —— 运行期多抽或少抽一次仍然会被对账抓到。

### ⚠️ 一条**被推翻**的"回归" —— 以及它为什么值得留在文档里

我一度把它写成「`build()` 慢约 10 倍（老 106ms / 新 481ms）」并报了两次。**那是假的**，
是我的测量夹具不对称造成的。真相：

| `build()` 一进程一次（`temp/probe_pre_ab.py`，各 3 次） | 老版 | 新版 |
|---|---|---|
| **两边都不烘音效** | 39 ms（37.5 / 42.7 / 39.0） | 40 ms（39.2 / 40.3 / 40.5） |
| **两边都烘音效** | 381 ms（399 / 322 / 381） | 408 ms（400 / 408 / 424）→ 新版慢 **约 7%** |

那 ~10 倍**全部**来自**音频烘焙线程**：`Sfx(True)` 在 `build()` 里起一条后台线程，用约 700ms
CPU 合成 41 条音效，和主线程**抢 GIL**。老版驱动一直设了 `M.SOUND_ENABLED = False`（不烘），
而新版读的是 `config.SOUND_ENABLED`（`root.py` 里刻意改成运行期读模块属性），我的探针**没设**它
⇒ 一边烘一边不烘，量出来的差就是烘焙的开销。

**结论：`build()` 两边持平（不烘 39 vs 40 ms）。** 都烘那一档新版慢约 7%，但那是烘焙线程抢
GIL 的**噪声区**（两边逐次在 320~425 ms 之间跳），别拿它下结论。**没有"10 倍"这种量级的回归。**

### ⚠️ 同一个夹具坑的**第二次**：顺序效应（2026-09-19）

`temp/probe_perf.py` 原来在**同一个进程里先跑老版、再跑新版** —— 新版永远吃"第二个跑"的亏

| 口径 | 新版 / 老版 |

而一次独立复核据此报出的「新版慢 5%」**用的是同一个有顺序效应的探针**。**两个方向都不成立，
真值是"对等"。** 探针已改成"起独立子进程 + 交替顺序"，并把判据从均值改成**中位**
（均值会被单个 16036 的离群样本拉到 0.88x）。

> 这是本工程第三次栽在"**夹具两边喂的输入不一样**"上（前两次：`build()` 那次一边烘一边不烘、
> `android_jni` 给了真闸门永远不会产出的组合）。共同点：**产出的数字看起来完全合理。**

⚠️ **这个错误本身比那个数更值得记**：我花了很久去 `RootWidget.__init__` 里找一个不存在的
慢行，把 `Button` / `Label` / `GameArea` / `WinPileFX` / `dp` / `sp` / 字体注册 / 字体目录
遍历 / `ball_texture` / GC / `style.kv` **挨个单独测了一遍**（全是 1~2ms），还写了
`faulthandler` 抓栈与调用级剖析器 —— 而剖析器对**生成器**会误计（`os.walk` 被算成 262ms，

**教训（与本工程一直在抓的那类缺陷同源）：夹具两边不同值，比代码错更难发现 ——
