# 1% Low 优化方案（v2）

更新：2026-09-20。**v1 已死**（降帧率换 1%low），死因见「已否定的方向」第 1 条。

> 本文只记录**真实呈现长帧**的优化路线。不比纯物理吞吐、不降分辨率、不关 MSAA、
> 不删动画、不隐藏正常 UI —— 与老版交接文档 `android/jiaojie.md:123-129` 同一口径。

---

## 〇、一句话现状

**我们的 Python 不是问题**（慢帧里 `_frame` 自算 0.01~0.58ms，165Hz 预算 6.06ms）。
**真问题是每一根慢帧都落在「1.35~1.45 个刷新周期」上** —— 即「**刚好错过一格 vsync，多等一整格**」。
把它压回 1.0，1%Low 就等于平均帧率。**这一仗跟帧率档无关，花平均帧买不到。**

## 二、已否定的方向（**死命题清单** —— 不许以原样复活）

| # | 方向 | 证伪依据 |
|---|---|---|
| 1 | **降帧率换 1%low** | Kivy 上限是**闸门**不是**钳位**（`_check_ready` 只对"还没到预算"的帧 usleep）⇒ 帧间隔逐元素 ≥ 原分布 ⇒ `1%Low_capped = min(1%Low_uncapped, cap)`。真机 0.70 的 1:1 比例正面证实 |
| 2 | **只压低部分阶段的帧率** | `n = max(1, int(len(gaps)*0.01))` 是**按帧数**取最慢 1% ⇒ 被压的那批**自己变成**最慢 1%。真机窗口里装杯占 46% ⇒ 只压装杯 = 1%Low 从 ~114 掉到 ~55 |
| 3 | **把显示模式请求与 cap 解耦** | 165Hz 面板配 120 上限 = 165/120 = 1.375 **不整除** ⇒ 拍频（老版实测：60Hz 屏上 120 上限比不设上限还慢，51.7 vs 60.3） |
| 4 | **Kivy `GraphicsCompiler` 重编译** | `temp/_gcc_probe.py`：385 条指令 → −0.003ms；3850 条 → +0.030ms（占 2.2%）。**标度阴性对照做了，尺子是灵的** |
| 5 | **减少画布指令条数** | 桌面实测只有 526/366 条；且 `on_draw ≈ 0.4µs × 条数` ⇒ 全部删光也只省 ~0.36ms |
| 6 | 预烘余额/统计的数字串 | 桌面实测 0.132 / 0.208ms，对照空标签 0.119ms ⇒ 和空转同价 |
| 7 | 调低 GC gen-0 阈值 | 配对实测：有回收的 91 次全 ≤1.087ms；那个 5.985ms 离群发生在**没有回收**的趟里 |
| 8 | 打开 `_GLYPH_ON` | 收益已被 v0.7.46「中奖大字预烘」兑现；`GlyphLabel` 全工程只用一处 |
| 9 | 「pyjnius 调 JNI 持 GIL 所以搬线程没用」 | 读源码：`with nogil:` 包住 `CallXMethodA` |
| 10 | 优化纯弹道模拟吞吐 | 物理约 1.71ms/**秒**，远低于预算 |
| 11 | 关 MSAA | 老版量过：ms=0 与 ms=2 的 on_flip 中位 12.51 vs 12.81ms（噪声内）；且在不做清单 |
| 12 | **用 C/Cython 重写游戏** | 我们全部 Python 只占 0.07ms ⇒ 最多省 0.07ms（预算的 1.2%），而代价是 `trace_parity` sha1 + `ast_parity` 681 个冻结函数 + 543 条台账全废。**且 Kivy 渲染核心本来就是 Cython** |
| 13 | 热点搬进 Java 类 | JNI 单次 ≈0.1ms（本工程 `_JNI_STAT` 夹具实测）⇒ 每帧调一次就亏回去 |

## 三、生态调研结论（2026-09-20）

- **Kivy / python-for-android 生态里没有任何一条讨论 120/165Hz 高刷，也没有任何一条讨论 1% low。** 只有零星的「帧率掉了」issue（kivy #6781 / p4a #2002 / kivy #8997）。
- **社区的通用清单我们基本吃透了**：widget 创建慢→已预烘；Cython→逻辑只占 0.1ms；atlas→字体子集化；`autoclass` 慢→已缓存类对象；阻塞活→发声/震动/落盘/守卫都搬了；`StencilView` 拖慢→**全工程零 `StencilView`**。
- **问题本身有官方解**：[Android Frame Pacing Library（Swappy）](https://developer.android.com/games/sdk/frame-pacing)。它的 `SWAPPY_SWAP_60FPS/30FPS` 就是「花平均帧」的官方形式，auto mode 会按前几帧平均时长自动降档。**但它要替换 `eglSwapBuffers`，在 SDL2 native 里 —— Python 侧够不到。**
- ⚠️ **Swappy 明确否掉了我们现在的做法**：「以渲染 API 允许的最快速度提交帧」→ buffer stuffing、多一帧延迟、**恶化帧率不一致**。
- ⚠️ **SDL 自己承认没解决**：vsync 状态启动时静默翻转（[#14642](https://github.com/libsdl-org/SDL/issues/14642)）、AChoreographer 支持还在提议（[#15013](https://github.com/libsdl-org/SDL/issues/15013)）、帧同步子系统还在 wishlist（[#10160](https://github.com/libsdl-org/SDL/issues/10160)）。
- ⚠️ **一条悬在我们全部结论上方的刀**：SDL 论坛「Uneven V-sync」帖指出「**有些 GPU 驱动不在 present 里阻塞，调用提前返回、绘制是异步的 ⇒ 围绕它量的时间不是真实帧时间**」。我们的 `_FRAME_SWAP` 正是这么量的。

## 附录：差额律的**独立复算**（2026-09-20）

新仪表（0.8.83）的判据全部挂在这条律上，所以它**必须自己算一遍**，不能引用子代理的结论
（当天已抓到两条编造/错记的"事实"，见第七节）。

**方法**：`android/temp/_real_dev_slow.txt` 是 14 组 × 5 帧的**慢帧邻域**，
所以只在**组内**做相邻配对（跨组不是相邻帧，配出来的数没有意义）。

```
组数 14   可配对样本 n = 56
差 (= dt − 主线程 − 等屏幕)  中位 1.92   最小 −0.36   最大 5.49
差_i + 上一帧body            中位 6.10   均值 6.27    最小 2.12   最大 20.97

T = (11/15)/cap   cap=120 → 6.111   cap=144 → 5.093   cap=165 → 4.444   cap=185 → 3.964
```

**⇒ 6.10 对 6.111（cap=120），差 0.2%。差额律成立。**

⚠️ 三点保留，别把它当成"已证明"：

1. 样本是**慢帧邻域**（14 个最慢帧各自上下 2 帧），**不是全窗口分布**。
2. 它**分不开 6.06（165Hz 一格 vsync）与 6.111（Kivy 睡眠常数）** —— 两者差 0.8%。
   能分开的只有一次 **cap 扫描**（`cap ∈ {120,165,185}`，看这个常数是否跟着 6.11/4.44/3.96 走）。
3. `最大 20.97` 说明**至少有一帧完全不吃这条律** —— 那一帧才是真正的"未知开销"，值得单独看。

⚠️ 子代理报的是 **n=34 / 中位 6.14**。中位对得上，**样本数不同**（应该是另一种配对口径，
比如只在 `差 > 0` 的帧上配对）。**数字不冲突，但口径要写清楚** —— 否则下次没人能复现。

### ⭐⭐ 不用重出 APK 就能跑新代码（`tools/emu/push_code.sh`）

**为什么能**（逐条实测过）：

| # | 事实 | 怎么验的 |
|---|---|---|
| ① | APK 是 **debuggable**（CI 跑 `buildozer android debug`）⇒ **`run-as` 能进应用私有目录** | `adb shell run-as org.danzhu.tiao id` → `uid=10052(u0_a52)` |

| ③ | **只在首次启动解压**，之后不覆盖 | push 一个标记文件 → 重启两次 → **它还在** |
| ④ | `.pyc` 的 magic **一致**（本机 Python 3.11 = APK 里的） | 两边都是 `a70d0d0a` |
| ⑤ | 模块树**一致** | 设备 30 个 `.pyc` ↔ 本工程 30 个 `.py`，**差集为空** |

⚠️ **三条边界**：
1. **日志头里的 `v0.8.xx` 不代表推的代码版本**（它读 `buildozer.spec`，那个不在 `app/` 里）
   ⇒ **验证代码版本只能看行为，不能看版本号。**
2. 不换资源（`assets/` `fonts/` `voice/`）与 `_python_bundle`（Python 本体）。
3. **只对 debug APK 有效**（release 包 `run-as` 会被拒）；出货仍走 CI。

**回滚**：`bash tools/emu/push_code.sh --restore`（回滚 `danzhu/`；`main.pyc`/`p4a/` 当时没单独备份，
要回滚它们得 `adb install -r` 重装）。
