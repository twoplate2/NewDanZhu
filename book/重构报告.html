1起点：为什么这件事值得认真做

老版是一个单文件 22,347 行的 Kivy 应用。它长成这样：

  • class RootWidget 从第 13,263 行写到第 21,433 行，8,171 行、154 个方法，把「游戏逻辑」和「界面」焊在一起 —— 同一个类里既有状态机、余额结算、随机数流，也有按钮底色、字号自适应、画布层序。
  • 想知道「改这个数会影响什么」，只能通读。
  • 想写一条自动化测试，没有缝 —— 状态、界面、时钟、随机会话全在一个对象里。

重写的目标定得很死，三条：

  1. 功能 1:1，一个不能少（玩家投诉过「你丢掉了落袋动画」）
  2. 行为逐位一致（不是「看着差不多」）
  3. 架构模块化、代码精简，性能不能降（可以变强）

只服务安卓。

2什么叫「一样」—— 先把验收口径钉死

这是整件事的地基。如果验收标准是「跑起来看着差不多」，那前面 10 处分歧一处也发现不了。

老版有两个性质，让「逐位对账」成为可能：

老版的性质为什么关键
android/main.py 可以无窗口 import库层逻辑（物理 / 盘面 / 球堆 / 音频合成）能在没有 GL 的机器上跑
同一随机种子 → 逐帧确定同一个输入序列，两版应产出同一个可观测轨迹

于是验收口径是：同一串脚本化输入，两版产出「逐位相等」的可观测轨迹。
而不是「启动看看像不像」。

3四层证据链

一条门禁只能证明一件事。所以搭了四层，每层的盲区不一样。

第 1 层  冻结基线    比 tests/golden/ 里采好的数据      → 快，但有分辨率下限
第 2 层  活体对账    直连老版代码，当场跑、当场比        → 无分辨率下限
第 3 层  轨迹对账    整局游戏的可观测轨迹，逐帧逐字节    → 最强的那个闸门
第 4 层  静态比对    函数体 / 签名 / 常量，AST 级        → 补行为门禁看不见的维度

3.1 第 1 层：冻结基线

tests/parity.py 有一半比的是 tests/golden/ 里采好的数据（几何坐标、280 条飞行轨迹、盘面配平、41 条音效波形的 sha1…）。

它有一个必须说清的弱点：有分辨率下限。实测把盘面权重 0.289 改成 0.290，它仍然全绿 —— 那个改动落不进采样的分辨力里。

tests/trace_parity.py 用同一份脚本分别驱动老版和新版，然后把两边产生的轨迹逐字节比：

剧本覆盖：12 发球（其中 3 发按住超 3 秒触发兜底自动发射）+ 两次切档 + 一次必中档中奖后不点击 + 飞行中按重置 + 长按标题 3 秒进跑分菜单 + 菜单内导航。

⚠️ 但它有两个必须自己承认的盲区

盲区一剧本外的输入，它一无所知。

「trace_parity 全绿」只等于「剧本覆盖到的那部分一致」，不等于「全部一致」。这不是理论担心 —— 剧本原先就没有「蓄力超 3 秒」和「飞行中重置」这两条分支，2026-09-19 才补进剧本（帧数 5,159 → 5,462，音效 266 → 275）。

盲区二它看不见「多做一次幂等调用」这一类缺陷。

它比的是可观测状态。一个幂等调用不改变任何一项 ⇒ 逐位相同、全绿、画面不变 —— 而代码确实多做了一次。

实测证明过：把 _render_skip 的修复回退掉，sha1 一模一样。⇒ 扩剧本对这个类别无效（因为多出的那次 _set_label_text 是幂等的）。

⇒ 这一类只能靠调用侧的判据抓：render_skip.py（行为）、act_gate.py（调用形状）、ast_parity.py（函数体）。

3.4 第 4 层：静态比对（AST 级）

行为门禁看不见「接线漂移 / 少调一次 / 搬错一个数」。所以又加了两条：

门禁比什么抓到了什么
ast_parity.py老版每个 def ↔ 新版对应函数的归一化函数体（去 docstring、归一化已知改名），差异集合必须与基线 tests/golden/ast_diff.txt 逐条相同159 处函数体差异，其中唯一一处真差异就是下面 §5 的第 5 条
sig_parity.py函数签名（参数名 + 默认值）+ 模块级大写的常量值5 条差异，逐条核过全良性

判据形式两者相同，也是从 fx_gates.py 借来的那套：

多一条 = 新版真漂了；少一条 = 门禁被削弱了；基线读不到 = 红。
（「没比」不等于「通过」。）

ast_parity 第一版是假的。它只记差异的名字，而 Game._controls 在老版叫 RootWidget._set_controls_enabled —— 名字对不上，整条落进「新版独有」桶里，函数体从不比对。实测往里注入那条漂移，第一版照样全绿。改成「新版独有的也冻函数体指纹」才真的抓得住。

sig_parity 补的是 ast_parity 自己挖的洞：后者的 _norm_dump 里有一句 node.args = ast.arguments(...) —— 把参数表整个抹掉，签名一个字都不比。而「默认参数值被改了一个数」正是本工程反复栽的那一类。

3.6 门禁本身也要被验：阴性对照

一条永远绿的闸比没有闸更糟 —— 它给你虚假的安全感。

所以每条门禁都配阴性对照：把修复回退掉 / 把闸门拆掉 / 把夹具打歪，必须判红。举几个真实例子：

4重构后的样子

4.1 一句话架构

把「游戏逻辑」和「界面」劈开。

danzhu/game.py :: Game          无头状态机 —— 六态迁移 / 账务 / 音效决策 / 时序
ui/root.py     :: RootWidget    界面壳   —— 建控件树 / 把事件画出来 / 把输入转回去

Game 不播声、不画界面，只产出一串 Ev 事件。UI 每帧 game.step(dt)，然后逐条派发。

这一刀是后面所有对账的前提 —— 因为「同一串输入 → 同一串可观测轨迹」变成了可测的东西。

RootWidget 那 8,171 行按职责再拆成三个 Mixin（ui_base / play / bench），老版的方法体一个字没动，只换了归属文件。

4.3 关于「代码只少了 4.6%」—— 这不是失败

外面容易误读这一条，所以说清楚：

  • 行数只降 4.6% 是刻意的。目标是 1:1 还原 —— 把 8,171 行的 God class 拆成模块，方法体一个字不动，行数本来就不会大降。
  • 真正降下来的是单点复杂度：最大单类 8,171 → 1,392 行；打包配置 6,668 → 81 行（老版那份里真配置只有 26 个键，其余全是注释）。
  • 而且新版多出了老版没有的东西：整个 tests/ 验收台（11,497 行）、事件管线、可注入的落盘口。这些是「变多」，但换来了可验证性。

一句话：这次重构卖的不是行数，是「可证明的一致性」。

5.2 挑三条最值得说的展开

① 时钟域：一个 trace_parity 永远看不见的缺陷

工程里有两把钟：

  • Game.now —— step(dt) 从 0 累加的模拟钟
  • time.time() —— 墙钟绝对值（约 1.7e9），WinPileFX 整个模块用它

一条「到点兜底」的判据，如果写侧取墙钟、比侧取模拟钟，那就是拿「~1.7e9 秒」去比「~20 秒」⇒ 恒假、兜底变死代码。

修法：取差值换算（两把钟都按真实秒推进）：

_ra = self._fx.reveal_at()
self._reveal_deadline = (
    _ra + 0.05 if not _ra
    else self.now + (_ra - time.time()) + 0.05)

这类缺陷在门禁下结构性不可见：轨迹台的假钟让两把钟都从 0 起、加同一串 dt ⇒ 逐位相等、trace_parity 全绿、看上去完全正常。

这又是一个「夹具自己制造绿」。⇒ 后来补了 tests/clock_domain.py 专门守这一类（不只守这一条）。

② 那个 try 罩了 22 行还是 5 行

老版：

try:                                    # main.py:20566
    with open(path) as f: cfg = json.load(f)
    ...                                 # 22 行解析，全在 try 里
except Exception:
    pass                                # 静默吞掉，照常进游戏

新版重构时被收窄成只罩 open()+json.load，22 行解析裸奔。

触发面很真实：json.loads('1e400') == inf，而 json.dump(float('inf')) 写出来的正是裸 Infinity（Python 的 json 默认接受）。⇒ 能被 json.load 读出 inf 的存档是合法 JSON，不走「解析失败」那条 except。

实测对照：

存档 {"max_plays":20,"rtp_target":1.2,"bet":100,"balance":1e400,"plays":7,"hits":3}
老版 → ('ok', max_plays=20, rtp=1.2, bet=100, balance=1000, plays=0, hits=0)
新版 → ('EXC', 'OverflowError', 'cannot convert float infinity to integer')

而这个异常落在 App.build() 里，那一句没有任何 try 兜 ⇒ 直接冒到 Kivy 主循环 ⇒ 启动即崩。老版同一份存档照常启动。

穷举验证：把两版全部代码行按 AST 标出「是否在 try 内」再逐行对账 —— 全工程只有这 22 行从「老版在 try 内」变成「新版在 try 外」。

③ 那句「每帧多跑一次幂等函数」

Game._controls 原来连发两条事件，而 controls 的处理函数首句就是 _restyle_buttons() ⇒ 同一帧执行 2 次（老版 1 次）。

它幂等 ⇒ 画面不变、trace_parity 逐位相同、21 条门禁一条都没红。

抓住它的是 ast_parity.py —— 而且只有它能抓：行为门禁比的是可观测状态，而「多做一次幂等调用」不改变任何一项。

修复后 Game._controls 的注释里写着：

只发 controls 一条，绝不在这里再发一条 restyle_buttons

5.3 顺手修掉的一个老版自己的 bug

sig_parity.py 采基线时逐条核差异，发现老版 _collide_arc 的签名是：

def _collide_arc(self, ..., frame=_ARC_FRAME):

_ARC_FRAME 是模块级可变计数器（逐帧递增），而默认参数在 def 那一行就求值 —— 于是它被冻死在 import 时刻的值（0）。

新版删掉了这个默认值（唯一调用点两边都显式传实参，行为等价）。

11.1 真机才能验的那一半

账本里有 43 条「机器未验」（代码在、逻辑也对，但只有真机上才成立）：

  • SoundPool 是否真的解码
  • Vibrator 是否真的震
  • 高刷模式系统是否受理
  • sched_setaffinity 是否真的锁核

它们的接口与聚合逻辑那一半已经有门禁（android_jni.py 24 项 + backend_chain.py 17 项）。剩下的是真机那一半 —— 本机是桌面，跑不了。

11.2 启动那 6.4% 必须在真机上复核

那 6.4% 的领先建立在 t_audio 只比 t_play 早 16 ms 上（上面那张图的第三、四行几乎贴着）。真机 SoundPool 解码更慢 ⇒ 临界路径可能翻转。

这一点不写成「稳赢」 —— 桌面的 6.4% 不能直接外推到手机。这是同一条纪律。

_boot_log 已经把判死它需要的全部时间戳落盘（「App.build 进入 / 建 UI 完成 / 第一帧 / 加载页摘除 / 启动总耗时」）。

11.3 打包

  • new_danzhu/ 还不是 git 仓库，而 build-apk.yml 的触发 / 缓存 / 产物路径都假定仓库根就是 new_danzhu。要发 APK 得让它自己 git init 成仓库根。
  • 打包体积已查明不是问题：云构建跑在仓库检出上，老版那 2,145 个 temp/ 文件从来没进过 APK（挡住它的是「作者从来不 git add 它」这条人工纪律）。新版已经把 temp/ 写进 .gitignore —— 用规则挡，不靠纪律。

--which new --verify 打两种口径，证明力完全不同：
