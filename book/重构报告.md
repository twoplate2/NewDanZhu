## 1. 起点：为什么这件事值得认真做

老版是一个**单文件 22,347 行**的 Kivy 应用。它长成这样：

- `class RootWidget` 从第 13,263 行写到第 **21,433** 行，**8,171 行、154 个方法**，把「游戏逻辑」和「界面」焊在一起 —— 同一个类里既有状态机、余额结算、随机数流，也有按钮底色、字号自适应、画布层序。
- 想知道"改这个数会影响什么"，只能通读。
- 想写一条自动化测试，**没有缝** —— 状态、界面、时钟、随机会话全在一个对象里。

重写的目标定得很死，三条：

1. **功能 1:1，一个不能少**（玩家投诉过"你丢掉了落袋动画"）
2. **行为逐位一致**（不是"看着差不多"）
3. **架构模块化、代码精简**，性能不能降（可以变强）

只服务安卓。

## 2. 什么叫「一样」—— 先把验收口径钉死

这是整件事的地基。**如果验收标准是"跑起来看着差不多"，那前面 10 处分歧一处也发现不了。**

老版有两个性质，让"逐位对账"成为可能：

| 老版的性质 | 为什么关键 |
|---|---|
| `android/main.py` 可以**无窗口 import** | 库层逻辑（物理/盘面/球堆/音频合成）能在没有 GL 的机器上跑 |
| **同一随机种子 → 逐帧确定** | 同一个输入序列，两版应产出**同一个可观测轨迹** |

于是验收口径是：

> **同一串脚本化输入，两版产出**逐位相等**的可观测轨迹。**

而不是「启动看看像不像」。

## 3. 四层证据链

一条门禁只能证明一件事。所以搭了四层，**每层的盲区不一样**：

```
第 1 层  冻结基线    比 tests/golden/ 里采好的数据      → 快，但有分辨率下限
第 2 层  活体对账    直连老版代码，当场跑、当场比        → 无分辨率下限
第 3 层  轨迹对账    整局游戏的可观测轨迹，逐帧逐字节    → 最强的那个闸门
第 4 层  静态比对    函数体 / 签名 / 常量，AST 级        → 补行为门禁看不见的维度
```

### 3.1 第 1 层：冻结基线

`tests/parity.py` 有一半比的是 `tests/golden/` 里采好的数据（几何坐标、280 条飞行轨迹、盘面配平、41 条音效波形的 sha1…）。

**它有一个必须说清的弱点：有分辨率下限。** 实测把盘面权重 `0.289` 改成 `0.290`，它**仍然全绿** —— 那个改动落不进采样的分辨力里。

### 3.2 第 2 层：活体对账

同一个 `parity.py` 的另一半**直连老版活体**：当场 import 老版、当场跑同样的输入、当场比。9 段里的 3 段是这种。

**没有分辨率下限，也不会被"重刷 golden 制造绿"这条后门绕过。** 要证明"真的没漂"，用这一层。

```
[绿] geo: 396 项逐位相符
[绿] 轨迹: 73053 项逐位相符
[绿] 哑火: 19200 项逐位相符
[绿] 盘面配平: 4200 项逐位相符
[绿] 音效合成: 83 项逐位相符
[绿] 活体轨迹(全字段): 79541 项逐位相符
[绿] 活体盘面配平(高分辨): 10500 项逐位相符
[绿] 球堆(装杯): 10470 项逐位相符
[绿] 活体球堆(生产参数): 75647 项逐位相符
                                              → 273,090 项
```

### 3.3 第 3 层：轨迹对账（最强的闸门）

`tests/trace_parity.py` 用**同一份脚本**分别驱动老版和新版，然后把两边产生的轨迹**逐字节比**：

| 段 | 规模 | 内容 |
|---|---|---|
| 帧 | **5,355 帧 × 8 字段** | state / power / ball(x,y,vx,vy) / balance / round_plays / plays / hits / fx |
| 状态迁移 | 51 项 | 每次迁移的帧号、时刻、from/to、原因 |
| 结算 | 8 项 | 槽位、投注、档位、结算前后余额、彩蛋标记 |
| 音效 | 256 条 | **真发出去的**那一声（过了五道闸）：名字/增益/节流/帧/时刻 |
| 布局 | 28 控件 × 2 段 | 每个控件的 (x, y, w, h) —— 这些数字是 `text_px` 算出来的，**字体一错它们全错** |

**当前：全绿，且除 `meta.driver` 外逐字节相同**（sha1 `2b8304864bfbc664df273795f489d76f434e0fcf`）。

剧本覆盖：12 发球（其中 3 发**按住超 3 秒**触发兜底自动发射）+ 两次切档 + 一次必中档中奖后不点击 + 飞行中按重置 + 长按标题 3 秒进跑分菜单 + 菜单内导航。

#### ⚠️ 但它有两个必须自己承认的盲区

**盲区一：剧本外的输入，它一无所知。**
"`trace_parity` 全绿"只等于"**剧本覆盖到的那部分**一致"，不等于"全部一致"。这不是理论担心 —— 剧本原先就没有"蓄力超 3 秒"和"飞行中重置"这两条分支，2026-09-19 才补进剧本（帧数 5,159 → 5,462，音效 266 → 275）。

**盲区二（更要紧）：它看不见"多做一次幂等调用"这一类缺陷。**
它比的是**可观测状态**。一个幂等调用不改变任何一项 ⇒ 逐位相同、全绿、画面不变 —— **而代码确实多做了一次**。

实测证明过：把 `_render_skip` 的修复**回退掉**，sha1 **一模一样**。⇒ **扩剧本对这个类别无效**（因为多出的那次 `_set_label_text` 是幂等的）。

⇒ 这一类只能靠**调用侧**的判据抓：`render_skip.py`（行为）、`act_gate.py`（调用形状）、`ast_parity.py`（函数体）。

### 3.4 第 4 层：静态比对（AST 级）

行为门禁看不见"接线漂移 / 少调一次 / 搬错一个数"。所以又加了两条：

| 门禁 | 比什么 | 抓到了什么 |
|---|---|---|
| `ast_parity.py` | 老版每个 `def` ↔ 新版对应函数的**归一化函数体**（去 docstring、归一化已知改名），差异集合必须与基线 `tests/golden/ast_diff.txt` **逐条相同** | 159 处函数体差异，其中唯一一处真差异就是下面 §5 的第 5 条 |
| `sig_parity.py` | **函数签名**（参数名 + 默认值）+ **模块级大写的常量值** | 5 条差异，逐条核过全良性 |

判据形式两者相同，也是从 `fx_gates.py` 借来的那套：

> **多一条 = 新版真漂了；少一条 = 门禁被削弱了；基线读不到 = 红。**
> （"没比"不等于"通过"。）

⚠️ **`ast_parity` 第一版是假的。** 它只记差异的**名字**，而 `Game._controls` 在老版叫 `RootWidget._set_controls_enabled` —— **名字对不上**，整条落进「新版独有」桶里，**函数体从不比对**。实测往里注入那条漂移，第一版**照样全绿**。改成「新版独有的也冻函数体指纹」才真的抓得住。

⚠️ **`sig_parity` 补的是 `ast_parity` 自己挖的洞**：后者的 `_norm_dump` 里有一句 `node.args = ast.arguments(...)` —— **把参数表整个抹掉**，签名一个字都不比。而"默认参数值被改了一个数"正是本工程反复栽的那一类。

### 3.6 门禁本身也要被验：阴性对照

**一条永远绿的闸比没有闸更糟** —— 它给你虚假的安全感。

所以每条门禁都配**阴性对照**：把修复回退掉 / 把闸门拆掉 / 把夹具打歪，**必须判红**。举三个真实例子：

| 门禁 | 阴性对照做了什么 | 结果 |
|---|---|---|
| `round_end.py` | 回退 `_round_end_ack` 的修复 | 判红 |
| `sound_gate.py` | 回退注入，改回读副本 | 判红，失败信息 `实得 ['peg3']` |
| `render_skip.py` | ① 不通知 UI ② 不复位标志 | 分别 0 帧 / 连续 80 帧，判红 |
| `act_gate.py` | 第①版只统计"坏"的调用点 ⇒ **夹具自检只在已经红的时候通过** | 发现后重写 |

⚠️ **`act_gate.py` 的第一版是空的**：它的豁免前缀 `BENCH_LOOP_PREFIX` 里包含了 `_bench` / `_hp` / `_start_bench` / `_start_hp` —— **恰好就是那 4 个我刚修好的调用点** ⇒ 门禁**永远绿**。是拿一条阴性对照试出来的（对照没红）。

## 4. 重构后的样子

### 4.1 一句话架构

**把「游戏逻辑」和「界面」劈开。**

```
danzhu/game.py :: Game          无头状态机 —— 六态迁移 / 账务 / 音效决策 / 时序
ui/root.py     :: RootWidget    界面壳   —— 建控件树 / 把事件画出来 / 把输入转回去
```

`Game` **不播声、不画界面**，只产出一串 `Ev` 事件。UI 每帧 `game.step(dt)`，然后逐条派发。

**这一刀是后面所有对账的前提** —— 因为「同一串输入 → 同一串可观测轨迹」变成了可测的东西。

`RootWidget` 那 8,171 行按职责再拆成三个 Mixin（`ui_base` / `play` / `bench`），**老版的方法体一个字没动，只换了归属文件**。

### 4.3 关于「代码只少了 4.6%」—— 这不是失败

外面容易误读这一条，所以说清楚：

- **行数只降 4.6% 是刻意的。** 目标是 **1:1 还原** —— 把 8,171 行的 God class 拆成模块，方法体一个字不动，行数本来就不会大降。
- 真正降下来的是**单点复杂度**：最大单类 **8,171 → 1,392 行**；打包配置 **6,668 → 81 行**（老版那份里真配置只有 26 个键，其余全是注释）。
- 而且新版**多出了老版没有的东西**：整个 `tests/` 验收台（11,497 行）、事件管线、可注入的落盘口。这些是"变多"，但换来了可验证性。
- 一句话：**这次重构卖的不是行数，是"可证明的一致性"。**

### 5.2 挑三条最值得说的展开

#### ① 时钟域：一个 `trace_parity` 永远看不见的缺陷

工程里有**两把钟**：

- `Game.now` —— `step(dt)` 从 0 累加的**模拟钟**
- `time.time()` —— **墙钟绝对值**（约 1.7e9），`WinPileFX` 整个模块用它

一条"到点兜底"的判据，如果**写侧取墙钟、比侧取模拟钟**，那就是拿「~1.7e9 秒」去比「~20 秒」⇒ **恒假、兜底变死代码**。

修法：取**差值**换算（两把钟都按真实秒推进）：

```python
_ra = self._fx.reveal_at()
self._reveal_deadline = (
    _ra + 0.05 if not _ra
    else self.now + (_ra - time.time()) + 0.05)
```

⚠️⚠️ **这类缺陷在门禁下结构性不可见**：轨迹台的假钟让两把钟**都从 0 起、加同一串 dt** ⇒ 逐位相等、`trace_parity` 全绿、看上去完全正常。

**这又是一个「夹具自己制造绿」。** ⇒ 后来补了 `tests/clock_domain.py` 专门守这**一类**（不只守这一条）。

#### ② 那个 `try` 罩了 22 行还是 5 行

老版：

```python
try:                                    # main.py:20566
    with open(path) as f: cfg = json.load(f)
    ...                                 # 22 行解析，全在 try 里
except Exception:
    pass                                # 静默吞掉，照常进游戏
```

新版重构时被**收窄**成只罩 `open()+json.load`，22 行解析**裸奔**。

触发面很真实：`json.loads('1e400') == inf`，而 `json.dump(float('inf'))` 写出来的正是裸 `Infinity`（Python 的 json 默认接受）。⇒ **能被 `json.load` 读出 `inf` 的存档是合法 JSON**，不走"解析失败"那条 `except`。

实测对照：

```
存档 {"max_plays":20,"rtp_target":1.2,"bet":100,"balance":1e400,"plays":7,"hits":3}
老版 → ('ok', max_plays=20, rtp=1.2, bet=100, balance=1000, plays=0, hits=0)
新版 → ('EXC', 'OverflowError', 'cannot convert float infinity to integer')
```

而这个异常落在 `App.build()` 里，**那一句没有任何 `try` 兜** ⇒ 直接冒到 Kivy 主循环 ⇒ **启动即崩**。老版同一份存档照常启动。

**穷举验证**：把两版全部代码行按 AST 标出「是否在 `try` 内」再逐行对账 —— 全工程只有这 22 行从「老版在 try 内」变成「新版在 try 外」。

#### ③ 那句"每帧多跑一次幂等函数"

`Game._controls` 原来连发两条事件，而 `controls` 的处理函数**首句就是** `_restyle_buttons()` ⇒ 同一帧执行 **2 次**（老版 1 次）。

它幂等 ⇒ 画面不变、`trace_parity` 逐位相同、**21 条门禁一条都没红**。

抓住它的是 `ast_parity.py` —— 而且**只有它**能抓：行为门禁比的是可观测状态，而"多做一次幂等调用"不改变任何一项。

修复后 `Game._controls` 的注释里写着：

> ⚠️⚠️ **只发 `controls` 一条, 绝不在这里再发一条 `restyle_buttons`**

### 5.3 顺手修掉的一个老版自己的 bug

`sig_parity.py` 采基线时逐条核差异，发现老版 `_collide_arc` 的签名是：

```python
def _collide_arc(self, ..., frame=_ARC_FRAME):
```

`_ARC_FRAME` 是**模块级可变计数器**（逐帧递增），而默认参数在 `def` 那一行**就求值** —— 于是它被**冻死在 import 时刻的值**（0）。

新版**删掉了这个默认值**（唯一调用点两边都显式传实参，行为等价）。

### 5.4 审计也不是全对：被推翻的那些

对抗性审计的价值不只是"找出问题"，还包括**它自己被证伪**。举两例：

| 报了什么 | 复核结论 |
|---|---|
| `_swap_wrap` 新增 `except Exception: return` ⇒ "包装失效是静默的，老版没有这个出口" | **一半被推翻**：老版 `main.py:5512-5516` 本来就有 `try/except: pass` 吞掉包装失败。事实核对为真，但"机制"那条子断言不成立 |
| `_audio_src_files` 的回退绕过 `nofile` 哨兵 | **被推翻**：老版指纹路径里**根本没有 `listdir`**，所以"老版在 listdir 失败时落到 nofile"这句在老版无对应代码 —— 属范畴错误 |

⚠️ 这就是为什么每条发现都要配 **2 个独立的怀疑者**（任务是**推翻**它，不是确认它）。

### 5.5 登记在案、但刻意没改的差异

有几处查出来是真的、但**判断为不值得改或不能改**，一律登记在案：

| 项 | 现状 | 为什么不改 |
|---|---|---|

## 6. 性能

用户口径：**可以变强，不能变弱。**

四个口径实测（桌面，**分进程 + 交替顺序 + 多采样取中位**）：

| 口径 | 老版 | 新版 | 结论 |
|---|---|---|---|
| **物理步进**（`benchmark_trajectories`，48 样本/边取中位） | 33,702 步/秒 | 33,734 步/秒 | ✅ **对等（1.001x）** |
| **整帧耗时**（900 帧含 `Window.flip()`） | p50 16.662 / p90 16.674 ms | p50 16.662 / p90 16.674 ms | ✅ **p50/p90 逐位相同** |
| **启动 `build()`**（两边都不烘音效） | 39 ms | 40 ms | ✅ 持平 |
| **启动到可玩**（冷启动加载页摘掉，12 样本/边） | 1.473 s | **1.378 s** | ✅ **新版快 94 ms（6.4%）** |

### 6.1 那 6.4% 是怎么来的

先说**失败的四条**（都实测过，都回退了）：

| 试的什么 | 对照结果 | 结论 |
|---|---|---|
| ① 把 `Sfx(...)` 提到 `build()` 第一句 | +45 vs +41 ms | 无可测收益 |
| ② 烘焙线程降 **OS 优先级** | +39 vs +41~45 ms | 无可测收益（**管不到 GIL**）|
| ③ `sys.setswitchinterval(0.001)` | **+837 ms** | **灾难性变差** |
| ④ 烘焙每音效 `sleep(0)` 让出 GIL | +49 vs +35~45 ms | 无可测收益 |

**前四条都在"抢"**（抢优先级、抢 GIL）。**第五条是"错开"**：把烘焙的**开工时刻**推迟到 `build()` 末尾（树建完了、首帧之前）。

| 相位 | 老版 | 新版（推迟后） | 差 |
|---|---|---|---|
| `t_build` | 1.077 | **0.583** | **−494 ms**（树构建不再被抢）|
| `t_frame1` | 1.224 | **0.793** | **−431 ms** |
| `t_audio` | 1.334 | 1.362 | +28 ms（烘焙晚起，但不争用）|
| **`t_play`** | **1.473** | **1.378** | **−94 ms（−6.4%）** |

**噪声地板**：`old vs old` 同口径 12 样本 = **−3 ms（−0.2%）** ⇒ −94 ms 远超噪声。

⚠️ **代价必须说清**：临界路径从「加载页地板」变成了「**烘焙**」—— `t_audio` 现在只比 `t_play` 早 **16 ms**。真机上音效解码更慢 ⇒ **这一条必须在真机上复核**（见 §11）。

### 6.2 那个 0.575x 的假信号 —— 一个值得单独讲的故事

物理步进这项，结论**被推翻过两次**才落到 1.001x：

| 探针口径 | 结果 | 判定 |
|---|---|---|
| 分进程（每进程只测**一版**）+ 交替，12 样本 | 新版 **0.575x** | ❌ **假** |
| **同进程**交替 + 两种起手顺序 | 1.010x / 1.000x | ✅ 可信 |
| **每个子进程内测两版**、交替，48 样本 | **1.001x** | ✅ **采用** |

那个 0.575x **复现了 3 次、超噪声地板 40 倍** —— 看起来完全像真的。我排除了 **13 个候选**才走到"这是夹具不对称"这一步：

> 烘焙改动（回退重测）· Kivy 窗口（给老版也建窗）· Python 线程（都只有 `MainThread`）· 导入期亲和性 · `sys.setswitchinterval`（都 0.005）· GC 阈值（都 `(700,10,10)`）· 冷启动 · 代码页未烫 · **缺页本身（完整参数烫透后仍 0.45x）** · `launch_ball`（Δ+0.0MB）· `advance_flight`（Δ+0.00MB）· `_PHYS_PROG`（同形）· 原生线程

**而关键旁证从一开始就有**：物理热路径 **7 个函数逐层字节码相同**（`benchmark_trajectories` / `physics_step` / `advance_flight` / `_collide_pegs` / `_collide_rect` / `_collide_arc` / `clamp`）⇒ **不可能是代码回归**。

⚠️ 并且我在自己的探针里**踩了本工程文档里记着的坑**：路径写成 `r"...\android\main.py"`，`\a` 被吃成 **BEL**（`DanZhu\x07ndroid`）—— `tests/backend_chain.py:38` 早就写着「**用 `os.path` 拼，不写反斜杠字面量**」。

## 7. 还能再优化吗？—— 先把目标拆开，再逐个实测

### 7.0 拆目标：哪条是硬的

| # | 目标 | 硬不硬 | 观测面 |
|---|---|---|---|
| 1 | 功能一个不少 | **硬** | 账本 543 条 |
| 2 | **行为逐位一致** | **最硬** | `trace_parity` sha1 + `parity` 273,090 项 + 28 条专项门禁 |
| 3 | 性能不下降 | 硬，但**可以变强** | 四个口径 |
| 4 | 模块化 / 可维护 | 手段，不是目的 | —— |
| 5 | 只服务安卓 | 硬 | —— |

**关键在这里**：目标是「**可观测行为**不变」，**不是「代码一字不动」**。这两者的差就是优化空间 —— 而空间有多大，**得量**。

### 7.1 方向一：帧内 CPU —— ❌ 已经没空间

**先得换口径。** 工程现成的「整帧耗时 p50 = 16.662 ms」**恰好是 1/60 s** —— 被 vsync 锁死了。CPU 从 5 ms 降到 3 ms，这个数**一动不动**。

真正该看的是 `_FRAME_SELF`（`play.py:212`）：`_frame` 在**主线程**花掉的毫秒数、**不含 `flip`**。

⚠️ 但我第一版探针是**手动连续调 `_frame`** —— 那会跳过 `Window.flip()`，Kivy 的纹理上传节奏跟着变 ⇒ 量出来的东西可能是**夹具造的**。所以在**真实事件循环**里复测：

```
真实事件循环 8 秒, 采到 340 帧
  中位 0.105 ms | 均值 0.359 | p90 0.165 | p99 0.905 | max 74.929

尖峰(> max(1ms, 30×中位)) 共 1 帧:
  74.929 ms   state=ready   fx_mode=idle   frame=0   ← 就是第一帧
```

⇒ **稳态帧内中位 0.105 ms，唯一的尖峰是第一帧**（启动成本，不是稳态问题）。
⇒ **桌面帧内没有可优化的空间** —— 0.1 ms 里大半是解释器本身的固定开销。

### 7.2 方向二：音效合成 —— ❌ 收益 1.5%，放弃

烘焙是**启动的临界路径**（656 ms CPU），所以它是最值得动的那个。profile 下来热点高度集中：

| 函数 | tottime 占比 |
|---|---|
| `_add_partials` | **63.6%** |
| `math.sin` | 15.7% |
| `_reverb` | 12.1% |
| `_pack` | 6.1% |

**约束先摆出来**：`parity.py` 有一项「音效合成: 83 项逐位相符」，**改波形就违约**。所以只能做**不碰浮点运算顺序/精度**的改写 —— 把热循环里的名字提到局部（省 `LOAD_GLOBAL` + `LOAD_ATTR`）、把恒定成立的分支拆出循环。

⚠️⚠️ **两个夹具给出了三个互相矛盾的结论**：

| 口径 | `_add_partials` | `_reverb` | 整库 |
|---|---|---|---|
| 固定顺序（原版先、优化版后） | −6.4% | −15.6% | **+1.0%** |
| 交替起手 + 每轮重造参数 | −1.7% | +2.5% | −3.5% |
| 交替起手 + 参数只备一份 | **−2.3%** | **+97.8%** | −1.5% |

第二版我又犯了同一个错：`fn(*mk())` 把「分配」混进了「计算」里。

**唯一稳定的是整库那一格：−1.5%（约 10 ms）。**
⇒ 为了 10 ms 去改两个**完全冻结**的核心合成函数 —— **不划算。这条路放弃。**

### 7.3 方向三：代码体积 —— ⚠️ 被 `ast_parity` 冻住了

先找重复：**函数体 AST 完全相同的重复 = 0 行**（说明拆模块时没留下复制粘贴，这是个好迹象）。

最大的单个目标是 `bench.py` 的 `_bench_frame_log` —— **795 行**（占 `bench.py` 的 15.5%）。

但它在 `ast_diff.txt` 里**不在**差异集合 ⇒ 说明它**两版函数体相同** ⇒ **它就是老版自己的形状**，不是「新版写得差」。

这引出一个必须量化的数：**`danzhu/` 里有多少行是「1:1 搬运、动不得」的？**

```
== danzhu/ 的函数按「可动性」分类（681 个函数 / 17,676 行函数体）==
  同名·函数体相同(完全冻结)    500 个 / 11,789 行  (66.7%)
  同名·已登记差异(冻结)        120 个 /  5,220 行  (29.5%)
  新版独有·已登记(冻结)         61 个 /    667 行  ( 3.8%)
  ⇒ 不更新基线时可动             0 个 /      0 行  ( 0.0%)
```

⇒ **函数体 100% 被冻结。** 剩下那 3,389 行（16.1%）是 import / 模块级常量 / 类属性 / 装饰器。

⚠️ **但「冻结」不等于「禁止」。** 改完跑 `python tests/ast_parity.py --freeze` 更新基线，本来就是**合法流程**。真正的代价是：

> **对那一次改动，`ast_parity` 当次失效** —— 它从「自动哨兵」退化成「我改完自己按了个确认键」。

所以那种改动必须**转移到别的门禁上兜底**（`trace_parity` + `parity` + 28 条专项），而且基线更新要**写明理由**，否则下次没人知道那几条差异是哪来的。

#### ⚠️ 但随后这一条被推翻了一半 —— 靶子不在代码里（2026-09-19 追加）

拆解「减少代码体积」这个目标时，做了两件原来没做的事：**量四种口径**、**拆 APK 实物**。

| 口径 | 现值 | 删注释 / 空行能减多少 |
|---|---|---|
| A 源码行数 | 21,333 行 | −5,116 行（**24.0%**） |
| B 源码字节 | 1,192.3 KB | −339 KB（−28%） |
| **C 字节码 `.pyc`** | **1,252.5 KB** | **−752 字节（−0.06%）** |
| **D APK 里** | 老版**全部**游戏代码 = **244.5 KB** | ≈ 0 |

**C 那一格是实测的**：把 31 个出货模块剥掉**全部**注释和空行（用 `tokenize` 剥，不是正则 ——
字符串里的 `#` 不是注释），再编译一遍：

```
基线              1,252.5 KB
剥掉注释+空行后    1,251.7 KB
差                −752 字节（−0.06%）
```

⇒ **删掉 5,116 行（占源码 24%），上设备的字节码只少 752 字节。**
这不是「收益小」，是**方向本身不成立** —— 注释不进字节码，唯一受影响的行号表几乎不动。

而拆开老版那个 APK 的 `assets/private.tar`（本机有实物）能看到：
**老版 22,347 行 / 1.4 MB 源码的全部游戏逻辑，编译成 `main.pyc` 只有 244.5 KB**；
同一个 tar 里**一个字体文件是它的 33 倍**（8,149.8 KB —— 那是子集化之前的版本）。

⇒ **代码在包里是零头。想减包体，靶子根本不在代码上。**

### 7.3b 真靶子在打包边界：833.7 KB 白进包

```
实测白进包的字节码   tests/ 781.6 KB + tools/ 46.0 KB + changelog/ 6.2 KB = **833.7 KB**
对比                出货代码本身才 1252.5 KB —— 白扔的是它的 67%
```

机制：`source.dir = .` 配 `source.include_exts = py,...` ⇒ buildozer 1.5.0 的 `_copy_application_sources` 按 `source.include_exts` **收全树**
（规则：全树 walk → **跳过隐藏路径段** → 过扩展名 → ⚠️ **无扩展名的文件也收**）。
实证：老版 APK 的 `private.tar` 里躺着 `sim_balance.pyc`(29.3 KB) 和
`bench_no_preflight.pyc`(45.8 KB) —— 两个纯 PC 工具脚本。

**已做**：CI 在构建前加一步剥掉 + 新增门禁 `tests/pack_scope.py` 守住（第 31 条）。
**全在打包配置里，一行游戏代码没碰** —— 符合「保持可读性」这条约束。
详见 `changelog/2026-09-19-体积拆解.md` 与 `changelog/2026-09-19.md` 第 20 条。

### 7.4 唯一做掉的那一个：台账 deque，省 14.2 MB

`Game.sounds` / `Game.settle_log` 是两条 `deque(maxlen=LOG_CAP)`。它们是**新版多留的一份** —— 老版的台账活在**外部 tap** 里。

实测（`temp/probe_mem.py`，tracemalloc）：

| `LOG_CAP` | 填满后常驻 |
|---|---|
| **20000**（改前） | **15.76 MB** |
| **2000**（改后） | **1.57 MB** |
| 500 | 0.39 MB |

**为什么 2000 就够** —— 三条都是读码/实测得到的：

1. `tests/trace.py:754` 只读 `settle_log[-1]` **一条**
2. `tests/round_end.py:222` 只读 `len(sounds)`
3. **全库对账全程只有 251 声**（这个数是原注释自己写的）

而且 —— **「为了让台账读全」这个理由本身就不成立**：`tests/trace.py` 的 `sound_log` / `settle_log` 是**驱动器自己那份 list**（`trace.py:263`），**不读 `Game` 这里**。

**为什么它零门禁代价**：

- 改的是**模块级常量**、不是函数体 ⇒ `ast_parity` 不管
- 老版**没有** `LOG_CAP` 这个同名常量 ⇒ `sig_parity` 的「两版都有的同名常量」交集为空

**验证输出**：

```
[绿] 除 meta.driver 外**逐字节相同**  sha1 2b8304864bfbc664df273795f489d76f434e0fcf   ← 一个字没变
对账结果: 全绿（parity 273,090 项）
```

⇒ **省 14.2 MB 常驻内存，行为逐位不变。**

### 7.5 结论

| 方向 | 结论 | 依据 |
|---|---|---|
| 帧内 CPU | **没空间** | 真实循环稳态中位 0.105 ms，唯一尖峰是第一帧 |
| 音效合成 | **收益 1.5%，放弃** | 三个夹具互相矛盾，只有整库那格稳定 |
| 代码体积 | **❌ 死路** | 删注释+空行 ⇒ 字节码只少 **752 字节（−0.06%）**（编译实测）；改函数体则撞冻结基线 |
| **包体积** | ✅ **已做，剥掉 833.7 KB** | 靶子在**打包边界**不在代码（§7.3b）—— 一行游戏代码没碰 |
| 台账内存 | ✅ **已做，省 14.2 MB** | 改常量，sha1 不变 |
| 启动（其它） | 未找到 | 临界路径是烘焙，动它就是动冻结函数 |

**一句话：在「行为逐位一致 + 门禁冻结基线」这个核心目标下，代码侧的优化空间已经被前面的工作榨干了。**

⚠️ 但**包体积那条路是新的** —— 它绕开了「改代码就得动冻结基线」这个死结，
因为它改的是**打包配置**，不是游戏逻辑。

**如果愿意付「那次改动失去 `ast_parity` 保护」这个代价，最值的一笔是**：
把 `_bench_frame_log`（795 行）这类巨型函数做表驱动改写 —— 但它**只减体积、不加性能**，
而且改完只能靠 `trace_parity` + `fx_gates` 兜底。
⚠️ **而且按 §7.3 的实测，它的字节码收益同样在千分之一量级 —— 不建议做。**

## 8. 教训：本工程反复栽的那些坑

这一节是给下一个接手的人看的。**这些坑的共同点是：产出的数字/结论看起来完全合理。**

### 8.1 「夹具两边喂的输入不一样」—— 栽了三次

| 事件 | 表象 | 真相 |
|---|---|---|
| `build()` "慢 10 倍" | 老版 106 ms / 新版 481 ms | 一边烘音效一边不烘（我漏设了 `SOUND_ENABLED`）|
| 物理步进 "新版慢 43%" | 0.575x，复现 3 次 | 分进程探针里新版多建了一个 Kivy 窗口 |
| `android_jni` 假绿 | 闸门全过 | 给了真闸门永远不会产出的组合 |

> **教训：量任何东西之前，先问一句"两边喂的输入真的一样吗"。**
> 这个错误**比代码错更难发现** —— 因为它产出的数字看起来完全合理。

### 8.2 「夹具自己制造绿」—— 轨迹台的假钟

`trace_parity` 是**最强的闸门**，但它的假钟让两把钟都从 0 起 ⇒ 跨时钟域的缺陷**逐位相等地绿**。

同类的还有：`tests/trace.py` 为了让轨迹可复现，把 `_cfg_post` **整链打桩关掉** ⇒ 异步落盘那条链在**所有门禁里跑过零次**。

> **教训：一条门禁"覆盖了什么"要看它打掉了什么桩，不看它写了多少断言。**

### 8.3 门禁会空转

- `act_gate.py` 第一版：豁免前缀**恰好包含**那 4 个刚修好的调用点 ⇒ 永远绿
- `fx_gates.py` 有 2 条判据原来比的是**源码字符串在不在** ⇒ ① 注释里出现同样字样就能喂绿它（**真踩过**：一条解释这个弱点的注释把另一条检查喂绿了）；② 函数定义了却没被调用，字符串照样在
- `history_io.py` 之前的门禁把路径桩写成 `_n + ".json"` ⇒ 产出的是 `plinko_bench_history_path.json` 这种**桩名**，**真文件名写错一个字母全绿**

> **教训：写"期望零命中"这类判据前，先在正确状态下跑一遍看它是否真通过；再在**故意弄坏**的状态下跑一遍看它是否真判红。**

### 8.4 「没看到」不等于「没有」

审计用"哪些功能改了没人会红"反查，一次找出 **8 条**门禁盲区（功能都在，缺的是判据）。

补门禁属于**超出 1:1 的增强**（老版也没有这些判据）—— 但正是它们让"一致性"从"我以为"变成了"机器证明"。

### 8.5 老版的注释和文档会骗人

实测已发现 **4 处注释与代码不符**：

| 常量 | 注释/文档 | 代码实际 |
|---|---|---|
| `MISFIRE_V_MAX` | 980 | **935** |
| `PEG_BOUNCE_VY_MAX` | 300 | **280** |
| `ARC_OUT_ANGLE` | 残留 25° | **35°** |
| `LAND_BOUNCE_MIN_VY` | 220 | **440** |

> **教训：任何数值都必须从代码的赋值行读。**

## 9. 一条质问

> **你说老代码是屎山，结果只是东西乱堆的仓库，优化后，性能也基本不变，只是请了一个家庭收纳整理师？**

这条质问有三层，逐层回答。

### 9.1 先说个事实：「屎山」这个词，报告里从没出现过

`grep -rn "屎山" README.md book/` = **0 命中**。

但这不重要 —— 重要的是：**按实测，这个词本来就用不上。**

「屎山」的判据是**改不动**：逻辑腐烂、补丁叠补丁、改一处崩三处、没人看得懂。而老版的实际性质恰恰相反，且**每一条都可实测**：

| 老版的性质 | 实测证据 |
|---|---|
| 行为确定 | 同一随机种子 → 逐帧确定；轨迹连跑多遍**逐字节相同**（905,878 字节） |
| 可集成 | 22,347 行**可以无窗口 import**，库层逻辑在没有 GL 的机器上跑得起来 |
| 可驱动 | 一份**外部脚本**能驱动它跑完一整局（12 发球 + 切档 + 中奖 + 长按），产出 5,355 帧完整轨迹 |
| 好用 | 600+ 次提交、玩家在玩，没有「改一处崩三处」的迹象 |

> **能被人从外部无窗口驱动、逐帧复现、连跑多遍一模一样的单文件，不是屎山。它是「堆得乱」。**

所以这一层质疑**成立**。正确的说法是「一间东西很多、没有分类、但每样东西都还好用的仓库」——用「屎山」是夸张。

### 9.2 性能基本不变、行数基本不变 —— 对，而且这是**刻意的**

- **性能不变是目标，不是失败。** 验收口径是「功能 1:1、行为逐位一致」。**任何一处性能变化都意味着行为可能已经变了。** 物理步进 1.001x 恰恰是「我没碰它」的证据 —— 而且热路径 7 个函数**逐层字节码相同**。
- **行数只降 4.6% 同理。** 目标是把 8,171 行的 God class **拆开**，方法体一个字不动 —— 拆开本来就不减行数。真正降的是**单点复杂度**（最大单类 −83%）。

如果这次的目标是「让游戏跑得更快」，那 1.001x 就是交白卷。**但目标不是。**

### 9.3 「只是请了个收纳整理师」—— 这一层不成立

收纳整理师**只整理，不验证**。他不会告诉你「你这 543 件东西一件没少」，也不会给你留下一台**能自动判错的机器**。

这次真正的产出有三样，都不是「整理」：

#### ① 一台能自动判错的机器 —— 老版**一条断言都没有**

老版 22,347 行、600+ 次提交，**自动化测试：0 条**。它的验收方式是「作者开窗玩几局」。

```
老版：改一行 → 开窗玩几局，几分钟，覆盖随机，靠眼睛
新版：改一行 → 28 条门禁 49 秒 ＋ 无头自测 26 秒
             ＝ 75 秒跑完 29 项，273,090 项逐位对账给你结论
```

**这个能力是「整理」给不出的。**

#### ② 一次全量审计 —— 老版从没被人这样读过

为了对账，老版被**逐行**过了好几遍：543 条功能账本逐条对照、120 处函数体差异逐条核、AST 级比对「哪些行在 `try` 里」、三轮对抗性审计。

**读一遍 22,347 行会发现的东西，收纳整理师不会发现**：

- 老版自己 **4 处注释与代码不符**（`MISFIRE_V_MAX` 注释 980、代码 935……）
- 老版自己 **2 处字体豆腐块**（「登记」的「登」、「杠杆」的「杆」不在它自己的字体子集里）
- 老版 `_collide_arc` 的 `frame=_ARC_FRAME` 是**冻死的默认值**

#### ③ 一处真的变快了

启动快 **94 ms（6.4%）**，而噪声地板是 −3 ms。

### 9.4 但有一条，我必须自己戳破

**那 10 处「真分歧」，10 处全是这次重构自己引入的。**

老版一条都没有。是**我在拆、在搬的过程中弄出来的**，然后用自己的门禁抓了回来。

逐条核对根因栏，写的全是「拆解 / 搬运这个动作本身」：

| # | 根因（原文摘录） |
|---|---|
| 1 | 「重构时被**收窄**成只罩 `open()+json.load`」 |
| 3 | 「拆模块后**这个同步点没人接手**」 |
| 4 | 「新版做成成员变量，却在 `reset_balance` 里清」 |
| 7 | 「状态机**搬进** `Game` 后，尾巴变成**无条件**跑完」 |
| 9 | 「老版是**一个方法**（字典与 children 同体），拆开之后只有 `Game` 这一个 `pop`」 |

⇒ **拿这 10 处当「重构的价值」是循环论证**：我制造了问题，再解决它，然后记功。

诚实的记账是：

| | 数量 | 归属 |
|---|---|---|
| 重构**引入**、又被自己的门禁抓回的缺陷 | **10** | **重构的代价**（被控制住了）—— 不是价值 |
| 老版固有、顺手修掉的 bug | **1** | `_collide_arc` 的冻死默认值（从未被触发） |

⚠️ **这一条比报告里任何一个数字都重要**：它把 §5 那张表的性质说清楚了 —— **那不是战功簿，是风险账单。**

顺带一个反事实：这 10 处**能不能避免**？

- 大部分能（比如 `try` 作用域，逐行搬就不会错）。
- 但有几处（#2 跨时钟域、#5 多发一条事件）**在搬的那一刻看起来完全正确** —— 只有事后做逐函数比对才发现。这正是最后落到 `ast_parity.py` / `sig_parity.py` 这类静态门禁的原因。

### 9.5 那到底值不值？

**取决于一件事：这个游戏以后还改不改。**

| 如果…… | 那么这次重构的价值 |
|---|---|
| 游戏**不再改了** | **≈ 0**。房子还是那个房子，只是东西摆整齐了 —— **质疑完全成立** |
| 游戏**还要继续改** | 价值在「**改动是可验证的**」：老版上改一个数只能开窗玩几十局碰运气；新版上 75 秒、27 万项逐位对账给结论 |

还有一条不该被忽略：**「不做」也是一个合理选项。** 老版跑得好好的，判定「它能用、不动它」完全成立 —— **重构不是无条件的正确**。

这次实际做的是一个**交换**：

> 用一次可验证的重写，换掉「以后每次改动都得靠开窗玩来验收」这个长期成本。

**这笔账划不划算，取决于你还要改多久。**

## 10. 另一个问题：改功能的时候，是不是更不容易出错、更省 token？

这条问得很实。但要答得先拆 —— **「更不容易出错」和「更省 token」是两件事，

下面**全部是实测**，样本不是我挑的 —— 用的是 `changelog/2026-09-19.md` 里那 10 处
**真分歧**的落点，它们本来就代表「这个工程真实发生过的改动」。
探针：`temp/probe_edit_cost.py`（可复跑）。

| ① 存档加载 | 7,242 行 | 32.4% | 1,186 行 |

但**这个数只在「不得不整文件读」时成立**，见下面的让步。

⚠️ **必须说清的让步**：老版**也可以**只读 200 行（Read 工具有 `offset/limit`）。
真正的问题是你**得先知道读哪 200 行** —— 而那件事靠的正是 §10.1 那个 43.5% 的跨度。
⇒ 「省」的准确说法是：**模块边界替你把「该读哪一段」划好了。**

⚠️ **反例**：⑩ 那格只省 **75.9%** —— 因为 `danzhu/ui/bench.py` 自己就有 **5,116 行**、
`BenchMixin` **4,984 行**。**拆分没有治好它。**

### 10.3 代码本体省不省？—— 不省

口径：目标函数体 + 它直接调用的、**同一容器内**的函数体。

| 改动点 | 老版 | 新版 |
|---|---|---|
| ⑦ 蓄力超时的渲染尾巴 | 1,295 行 / 34 个被调 | 160 行 / 2 个 |
| ⑤ 界面输入锁 | 115 行 / 4 个 | 23 行 / 1 个 |
| ① 存档加载 | 99 行 / 5 个 | 72 行 / 1 个 |
| ⑩ 跑分上锁 | 88 行 / 4 个 | 38 行 / 2 个 |
| ⑧ 落盘 | 67 行 / 3 个 | 35 行 / 0 个 |
| ⑨ 隐藏档按钮 | 20 行 / 1 个 | 18 行 / 0 个 |
| **⑥ 音色变体流**（唯一反而变大的） | **89 行 / 3 个** | **103 行 / 2 个** |

**这一栏才是诚实的答案：重构没有让代码变短。** ⑥ 甚至变大了。

⚠️ 而且这一栏**有口径偏差，我把它写出来而不是藏起来**：老版所有函数在同一个容器里，
「同容器内被调」能数到 34 个；新版的 `_frame` 在 `PlayMixin` 里，它调 `self.game.xxx`
（**跨容器**）就不计入 ⇒ **新版这一栏被系统性低估**。
⇒ **这个对比只能当量级参考，不能当精确账。**

**拆分的代价是真的**，而且在小改动上体现得最明显：

| 代价 | 实例 |
|---|---|
| 跨文件追踪 | `⑧ 落盘` 一个改动横跨 **3 个文件**（`game.py` / `platform/device.py` / `ui/root.py`） |
| 协议两边改 | `④ 去重闸` 老版是**一个匿名闭包**；新版拆成 `game.py` 的 `show_round_end` + `play.py` 的 `_show_round_end`，**改一边得想着另一边** |
| 新增一条 `Ev` | 要在 `game.py` 发、在 `ui/*.py` 收 |

### 10.4 更不容易出错吗？—— 是。但功劳不在「整齐」

这一条不是判断，是**今晚实测的反馈周期**：

```
python -m py_compile danzhu/game.py      166 ms
python tests/sig_parity.py               567 ms     ← 签名漂了没
python tests/ast_parity.py             1,483 ms     ← 函数体漂了没
全部 30 条门禁                        84,965 ms     ← 约 85 秒，rc=0
```

**老版这三条一条都没有**（22,347 行 / 600+ 次提交 / 自动化测试 0 条）。
改错了唯一的反馈是**开窗玩** —— 而 §5.1 那 10 处真分歧**全部会静默发作**
（画面照常、余额照跳，只有逐位对账才现形）。**开窗玩看不见其中任何一处。**

⚠️ 所以准确的说法是：

> **不是「新版不容易写错」，是「新版写错了会被抓住」。**

代码整齐度本身不产生这个效果 —— **一个摆得整整齐齐的屎山，照样没人拦你改坏它。**

### 10.5 ⚠️ 就在写这一节的时候，我抓到了自己的反例

为了量「改动的上下文成本」，我顺手复核了本报告里的几个数字。**三个是错的** ——
但错法分两类，得分开说：

| 报告里写的 | 实测 | 性质 |
|---|---|---|
| `RootWidget` **8,263 行** / 170 个方法 / 写到第 **21,526** 行 | **8,171 行** / 154 个方法 / 写到第 **21,433** 行 | **纯错** —— 老版从没动过，这个数追不到任何口径 |
| 最大单类 `Game` **1,627 行** | **1,392 行**（类体；`game.py` **文件**是 1,633 行） | **口径错** —— 拿文件行数冒充类行数 |
| `danzhu/` **21,065** / 合计 **21,327** | **21,071** / **21,333** | **漂移** —— 那是 09-18 的值，09-19 改完没同步 |

`8,263` 追不到口径是有实据的：`RootWidget` 在 `main.py:21433` 就结束了
（最后一行是 `_FRAME_END[0] = time.perf_counter()`），再往后是 `# App 入口` 注释块；
而 21,525 附近是 `VEIL_TITLE_SWEEP` 那批**模块级**常量，跟这个类毫无关系。

**这三个数支撑着「最大单类 −80%」这个结论。** 修正后是 **−83%**（8,171 → 1,392）——
方向没变，但这不改变「它是错的」。

**而发现它的时候，工程处在什么状态？**

> 30 条门禁全绿 · `trace_parity` sha1 逐字节相同 · `parity` 273,090 项全绿 ·
> `--selftest` rc=0 —— **没有一条门禁看得见文档。**

门禁锁的是**代码行为**；上一版报告里写的数字，**没有任何东西在管**。

⇒ 这恰好是对「更不容易出错吗」的**部分否定**：
**代码那一半被锁住了，文档那一半是我在裸奔。**

> ⚠️ **而且连"修正"这个动作本身也不干净。** 第一轮我照 grep 结果改了 **31 处**，
> 复查时又扫出 **8 处漏网**（「`RootWidget` 那 8,263 行按职责再拆成三个 Mixin」这类句子 ——
> 第一轮的关键词没盖到它）。⇒ **改文档这件事，只有我自己在复核，而且第一遍没复核干净。**

**第三个例证，就在同一个小时里。** 修完上面这些、往 `changelog/2026-09-19.md` 写记录时，
我写了一句「`README.md` 里那句『`td.num` 不能放长注解』」—— 而 **`README.md` 里根本没有那句话**：

```
$ grep -n "td.num\|nowrap\|表格" changelog/README.md
(空)
```

是我写的时候凭空引的 —— **和上面那三个数字是同一种病：写了没核实的话。**
这一条**没有删掉，留在 changelog 里当证据**。

⇒ 所以「更不容易出错吗」的答案得再收窄一格：

> **不只是「文档没有门禁」—— 是「我这个人写文档时也不可靠」。**
> 代码那边至少有 30 条机器闸门兜着；文档这边**兜底的只有我自己，而我自己刚刚连错三次**。

（修正记录见 `changelog/2026-09-19.md` 第 18 条。）

### 10.6 新版自己引入的**新**出错方式

## 11. 边界：还没做的 / 做不到的

诚实列出来，不含糊：

### 11.1 真机才能验的那一半

账本里有 **43 条「机器未验」**（代码在、逻辑也对，但**只有真机上才成立**）：

- SoundPool 是否**真的解码**
- Vibrator 是否**真的震**
- 高刷模式系统**是否受理**
- `sched_setaffinity` 是否**真的锁核**

它们的**接口与聚合逻辑那一半已经有门禁**（`android_jni.py` 24 项 + `backend_chain.py` 17 项）。**剩下的是真机那一半 —— 本机是桌面，跑不了。**

### 11.2 ⚠️ 启动那 6.4% 必须在真机上复核

那 6.4% 的领先建立在 `t_audio` 只比 `t_play` 早 **16 ms** 上。真机 SoundPool 解码更慢 ⇒ **临界路径可能翻转**。

**这一点不写成"稳赢"** —— 桌面的 6.4% 不能直接外推到手机。这是同一条纪律。

`_boot_log` 已经把判死它需要的全部时间戳落盘（「App.build 进入 / 建 UI 完成 / 第一帧 / 加载页摘除 / 启动总耗时」）。

### 11.3 打包

- **`new_danzhu/` 还不是 git 仓库**，而 `build-apk.yml` 的触发/缓存/产物路径都假定**仓库根就是 `new_danzhu`**。要发 APK 得让它自己 `git init` 成仓库根。
- 打包体积**已查明不是问题**：云构建跑在仓库检出上，老版那 2,145 个 `temp/` 文件**从来没进过 APK**（挡住它的是"作者从来不 `git add` 它"这条**人工纪律**）。新版已经把 `temp/` 写进 `.gitignore` —— **用规则挡，不靠纪律**。
